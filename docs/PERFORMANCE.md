# パフォーマンスとモバイル運用

## 品質方針

HITBOX SNAPは、画像読み込み時に必ず`@imgly/background-removal`で被写体を抽出します。色差だけを使う簡易マスクへフォールバックしません。保存・コピー・共有・背景変更は抽出完了後に有効になります。

抽出マスクから複数の食らい判定を作り、同タイプの重複矩形は合成して外周だけを描画します。速度改善のために矩形を個別strokeすると内側の重複線が出るため禁止です。

## モデル取得と進捗

- モデル: `isnet_quint8`
- 初回転送量: 約42MB
- 配信: `@imgly/background-removal`が利用するCDN
- キャッシュ: ブラウザキャッシュ。2回目以降も端末・ブラウザ設定により再取得される場合があります
- 進捗表示: モデル取得5〜65%、推論66〜94%、仕上げ96〜100%

処理中はスピナー、走査線、対戦ボックス、プログレスバーを表示します。CSSアニメーションはメインスレッドが混雑していても動きやすいtransform中心のスピナーを含めます。

## モバイルのメモリ対策

キュピーン猫（[InspirationCat](https://github.com/nyanko3141592/InspirationCat)）の実装を参考にしています。

- スマホではWebGPUを使わずCPU/WASMを使用
- モデル入力は1024pxから開始
- メモリ確保エラー時は768px、512pxの順で自動再試行
- 画像の解析・再試行は端末内で完結し、画像をサーバーへ送らない

Safariで「このページを開けません」と表示される場合は、OSによるタブ終了やメモリ不足が疑われます。まず他の重いタブを閉じて再読み込みします。再現確認では端末、OS、ブラウザ、画像のおおよその画素数、何%で停止したかを記録します。

## 編集時の最適化

- PCの編集画像: 長辺最大2048px
- スマホの編集画像: 長辺最大1280px
- 低性能スマホ: 長辺最大1024px
- pointermoveは`requestAnimationFrame`単位にまとめる
- 元画像、選択背景、影の合成結果をキャッシュする
- 重複輪郭用の作業Canvasは毎フレーム生成せず再利用する
- PNG保存は`toBlob`で非同期化する
- 作例とデモはWebPを使用し、JPEGは互換用に残す

## 回帰確認

変更後は最低限、スマホ幅390×844で次を確認します。

1. 画像選択直後にローディング演出と進捗率が表示される
2. 被写体抽出が完了するまで保存・共有が無効
3. 抽出後に複数の食らい判定が生成される
4. 重複矩形の内側輪郭が表示されない
5. 保存と背景変更が動く
6. 横方向へ不要にスクロールしない
7. モバイルの「写真に保存」がPNG付き共有シートを開き、非対応環境ではPNG保存へフォールバックする

静的配信の確認には次を使います。

```bash
bash scripts/verify-deployment.sh https://hitbox.nya3neko2.dev
```
